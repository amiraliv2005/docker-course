# بررسی خط‌به‌خط Dockerfile پروژه NetBox

## ۱. معرفی فایل

در این بخش، Dockerfile پروژه NetBox را بررسی می‌کنم. هدف این است که مشخص شود هر دستور چه کاری انجام می‌دهد و حذف آن چه تأثیری روی فرایند ساخت Image یا اجرای برنامه می‌گذارد.

منبع فایل:

https://github.com/netbox-community/netbox-docker/blob/release/Dockerfile

این Dockerfile از روش Multi-stage Build استفاده می‌کند و دو مرحله اصلی آن `builder` و `main` هستند.

## ۲. مرحله Builder

مرحله `builder` برای آماده‌سازی محیط ساخت و نصب وابستگی‌های پایتون استفاده می‌شود. در این مرحله ابزارهایی نصب می‌شوند که ممکن است برای آماده‌سازی بعضی کتابخانه‌ها لازم باشند.

### تعیین Image پایه و نام مرحله

```dockerfile
ARG FROM
FROM ${FROM} AS builder
```

دستور `ARG FROM` متغیری به نام `FROM` تعریف می‌کند تا Image پایه هنگام ساخت قابل تنظیم باشد.

دستور `FROM` Image پایه مرحله را مشخص می‌کند و با `AS builder` نام این مرحله را `builder` می‌گذاریم.

اگر این بخش حذف شود، مرحله ساخت با این ساختار تعریف نمی‌شود و دستورهای بعدی که به محیط پایه یا نام مرحله وابسته‌اند، درست کار نخواهند کرد.

### کپی کردن ابزار uv

```dockerfile
COPY --from=ghcr.io/astral-sh/uv:0.12 /uv /usr/local/bin/
```

این دستور فایل اجرایی `uv` را از Image مشخص‌شده کپی می‌کند. این ابزار برای مدیریت محیط پایتون و نصب وابستگی‌ها استفاده می‌شود.

اگر حذف شود، دستورهای بعدی که از `/usr/local/bin/uv` استفاده می‌کنند، اجرا نخواهند شد؛ مگر اینکه این ابزار از راه دیگری فراهم شده باشد.

### نصب بسته‌های موردنیاز ساخت

در این بخش با `apt-get update` فهرست بسته‌ها به‌روز می‌شود و با `apt-get install` ابزارها و کتابخانه‌های لازم نصب می‌شوند.

بسته‌هایی مثل `build-essential`، `python3-dev` و کتابخانه‌های توسعه برای آماده‌سازی وابستگی‌ها استفاده می‌شوند.

اگر بسته‌ای که برای ساخت یکی از وابستگی‌ها لازم است حذف شود، ممکن است نصب آن وابستگی با خطا مواجه شود.

در انتهای این بخش دستور زیر محیط مجازی پایتون را ایجاد می‌کند:

```dockerfile
&& /usr/local/bin/uv venv /opt/netbox/venv
```

اگر این دستور اجرا نشود، مسیر محیط مجازی موردانتظار ایجاد نمی‌شود و نصب وابستگی‌ها ممکن است در محیط نادرست انجام شود.

### کپی فایل‌های وابستگی

```dockerfile
ARG NETBOX_PATH
COPY ${NETBOX_PATH}/requirements.txt requirements-container.txt /
ENV VIRTUAL_ENV=/opt/netbox/venv
```

`ARG NETBOX_PATH` مسیر پروژه را هنگام Build مشخص می‌کند.

دستور `COPY` دو فایل وابستگی را به محیط ساخت منتقل می‌کند تا مراحل نصب از آن‌ها استفاده کنند.

دستور `ENV` مسیر محیط مجازی پایتون را در متغیر `VIRTUAL_ENV` قرار می‌دهد.

اگر فایل‌های وابستگی کپی نشوند، مرحله نصب کتابخانه‌ها فایل‌های موردنیازش را پیدا نمی‌کند. اگر متغیر محیط مجازی حذف شود، رفتار دستورهای بعدی ممکن است تغییر کند و باید مسیر محیط پایتون به شکل دیگری مشخص شود.

### اصلاح فایل‌های وابستگی و نصب کتابخانه‌ها

در این بخش، با `sed` بعضی وابستگی‌ها اصلاح می‌شوند و سپس `uv pip install` کتابخانه‌های موردنیاز را نصب می‌کند.

```dockerfile
RUN \
    sed -i -e '/gunicorn/d' /requirements.txt && \
    sed -i -e 's/social-auth-core/social-auth-core\[all\]/g' /requirements.txt && \
    sed -i -e 's/django-storages/django-storages\[azure,boto3,dropbox,google,libcloud,sftp\]/g' /requirements.txt && \
    /usr/local/bin/uv pip install \
      -r /requirements.txt \
      -r /requirements-container.txt
```

خط اول، وابستگی `gunicorn` را حذف می‌کند؛ چون این Image از Granian استفاده می‌کند.

دو دستور بعدی، قابلیت‌های اضافی موردنیاز برای `social-auth-core` و `django-storages` را به وابستگی‌ها اضافه می‌کنند.

در پایان، کتابخانه‌های فهرست‌شده در هر دو فایل نصب می‌شوند.

اگر هر کدام از این اصلاحات حذف شود، ممکن است وابستگی‌ها با تنظیمات موردنیاز پروژه هماهنگ نباشند. اگر مرحله نصب حذف شود، محیط مجازی شامل وابستگی‌های لازم نخواهد بود و اجرای NetBox احتمالاً با خطا مواجه می‌شود.

## ۳. مرحله Main

مرحله `main` برای ساخت Image نهایی استفاده می‌شود. در این مرحله فقط محیط و فایل‌های لازم برای اجرای NetBox آماده می‌شوند.

### تعیین مرحله اصلی

```dockerfile
ARG FROM
FROM ${FROM} AS main
```

این دستورها Image پایه مرحله نهایی را مشخص می‌کنند و نام مرحله را `main` می‌گذارند.

مرحله `main` از مرحله `builder` جداست؛ بنابراین فایل‌ها و ابزارهای مرحله قبل فقط در صورتی وارد Image نهایی می‌شوند که به آن کپی شوند یا از مسیر دیگری در دسترس باشند.

### نصب بسته‌های موردنیاز زمان اجرا

در این بخش بسته‌هایی مانند `python3`، `libpq5`، `curl`، `tini` و کتابخانه‌های زمان اجرا نصب می‌شوند.

تفاوت مهم این است که `libpq-dev` در مرحله ساخت، فایل‌های توسعه موردنیاز کامپایل را فراهم می‌کند؛ اما `libpq5` کتابخانه زمان اجرای کلاینت PostgreSQL است و به‌خودی‌خود سرور PostgreSQL نیست.

در انتهای دستور، مسیر فهرست بسته‌های APT پاک می‌شود:

```dockerfile
&& rm -rf /var/lib/apt/lists/*
```

این کار فضای اشغال‌شده توسط فهرست بسته‌ها را کاهش می‌دهد.

اگر بسته‌ای که برای اجرای NetBox یا اسکریپت‌های آن لازم است حذف شود، ممکن است برنامه در زمان اجرا با خطای نبود کتابخانه یا ابزار مواجه شود.

### انتقال خروجی‌های مرحله Builder

```dockerfile
COPY --from=builder /usr/local/bin/uv /usr/local/bin/
COPY --from=builder /opt/netbox/venv /opt/netbox/venv
```

این دستورها ابزار `uv` و محیط مجازی حاوی وابستگی‌ها را از مرحله `builder` به مرحله `main` منتقل می‌کنند.

اگر محیط مجازی کپی نشود، Image نهایی کتابخانه‌هایی را که در مرحله قبل نصب شده‌اند در مسیر موردانتظار نخواهد داشت.

### کپی کردن سورس NetBox و فایل‌های پیکربندی

```dockerfile
ARG NETBOX_PATH
COPY ${NETBOX_PATH} /opt/netbox
COPY --from=builder /requirements.txt /requirements-container.txt /opt/netbox/
```

این دستورها سورس پروژه و فایل‌های وابستگی اصلاح‌شده را به Image نهایی منتقل می‌کنند.

اگر سورس پروژه کپی نشود، فایل‌های لازم برای اجرای NetBox در مسیر موردانتظار وجود نخواهند داشت.

### کپی فایل‌های مخصوص Docker

دستورهای `COPY` بعدی فایل‌های پیکربندی، اسکریپت‌های اجرا، فایل بررسی سلامت، تنظیمات LDAP، تنظیمات Granian، پوشه پیکربندی و نسخه NetBox را به مسیرهای مشخص‌شده منتقل می‌کنند.

این فایل‌ها رفتار NetBox را با محیط Docker هماهنگ می‌کنند.

اگر یک فایل ضروری حذف شود، ممکن است تنظیمات درست اعمال نشوند یا اسکریپت مربوط به اجرا و بررسی سلامت در دسترس نباشد. تأثیر دقیق حذف هر فایل به این بستگی دارد که در کدام بخش پروژه استفاده می‌شود.

### تعیین پوشه کاری

```dockerfile
WORKDIR /opt/netbox/netbox
```

این دستور پوشه کاری پیش‌فرض را تعیین می‌کند. دستورهای بعدی که مسیر نسبی دارند و فرایندهایی که از این پوشه شروع می‌شوند، از این مسیر استفاده می‌کنند.

اگر حذف شود، پوشه کاری ممکن است مسیر پیش‌فرض Image پایه باقی بماند و دستورهای وابسته به مسیر فعلی در محل اشتباه اجرا شوند.

### ایجاد کاربر و تنظیم دسترسی‌ها

```dockerfile
RUN useradd --home-dir /opt/netbox/ --no-create-home --no-user-group --system --shell /bin/false --uid 999 --gid 0 netbox \
    && mkdir -p static media local \
    && chown -R netbox:root media reports scripts \
    && chmod -R g+w media reports scripts \
    && cd /opt/netbox/ && SECRET_KEY="dummyKeyWithMinimumLength-------------------------" /opt/netbox/venv/bin/zensical build \
        --config-file /opt/netbox/mkdocs.yml \
    && DEBUG="true" SECRET_KEY="dummyKeyWithMinimumLength-------------------------" /opt/netbox/venv/bin/python /opt/netbox/netbox/manage.py collectstatic --no-input \
    && echo "build: Docker-$(cat /opt/netbox/VERSION)" > /opt/netbox/netbox/local/release.yaml
```

این بخش چند کار را انجام می‌دهد:

- کاربر سیستمی `netbox` را ایجاد می‌کند.
- پوشه‌های لازم را می‌سازد.
- مالکیت و مجوزهای دسترسی بعضی پوشه‌ها را تنظیم می‌کند.
- فایل‌های مستندات را با `zensical build` تولید می‌کند.
- فایل‌های استاتیک Django را با `collectstatic` جمع‌آوری می‌کند.
- فایل `release.yaml` را برای ثبت نسخه Build ایجاد می‌کند.

اگر این دستور حذف شود، کاربر و پوشه‌های لازم ایجاد نمی‌شوند و فایل‌های مستندات، فایل‌های استاتیک یا اطلاعات نسخه نیز تولید نخواهند شد.

ایجاد کاربر با `useradd` به‌تنهایی ثابت نمی‌کند که Container در زمان اجرا با همان کاربر اجرا می‌شود؛ برای مشخص کردن کاربر واقعی اجرا باید تنظیمات نهایی Image و اسکریپت‌های اجرا هم بررسی شوند.

### تعریف متغیرهای محیطی

```dockerfile
ENV LANG=C.utf8 PATH=/opt/netbox/venv/bin:$PATH VIRTUAL_ENV=/opt/netbox/venv UV_NO_CACHE=1
```

این دستور زبان و محیط اجرای برنامه، مسیر محیط مجازی پایتون و تنظیم مربوط به کش `uv` را مشخص می‌کند.

اگر این متغیرها حذف شوند، محیط اجرا ممکن است از مقادیر پیش‌فرض استفاده کند و دستورهای وابسته به مسیر محیط مجازی یا رفتار موردانتظار `uv` درست عمل نکنند.

### تعریف ENTRYPOINT و CMD

```dockerfile
ENTRYPOINT [ "/usr/bin/tini", "--" ]
CMD [ "/opt/netbox/docker-entrypoint.sh", "/opt/netbox/launch-netbox.sh" ]
```

`ENTRYPOINT` مشخص می‌کند که `tini` به‌عنوان فرایند اولیه اجرا شود. `CMD` فرمان‌های پیش‌فرضی را تعیین می‌کند که به آن داده می‌شوند.

اسکریپت `docker-entrypoint.sh` برای آماده‌سازی محیط اجرا استفاده می‌شود و `launch-netbox.sh` فرایند راه‌اندازی NetBox را انجام می‌دهد.

اگر `ENTRYPOINT` حذف شود، `tini` دیگر به شکل تعریف‌شده اجرا نمی‌شود. اگر `CMD` حذف شود و فرمان جایگزینی ارائه نشود، `tini` فرمان پیش‌فرضی برای اجرا نخواهد داشت.

### LABEL

```dockerfile
LABEL netbox.original-tag="" \
      netbox.git-branch="" \
      netbox.git-ref="" \
      netbox.git-url=""
```

این بخش فراداده‌هایی درباره Image نگه می‌دارد؛ مانند تگ اصلی، شاخه Git، مرجع Git و نشانی مخزن.

اگر حذف شود، این اطلاعات برچسبی در Image ثبت نمی‌شوند، اما صرف حذف آن‌ها لزوماً اجرای اصلی NetBox را مختل نمی‌کند.

## ۴. اجرای عملی

در این قسمت، دستورهای ساخت Image و بررسی تاریخچه آن را اجرا می‌کنم و خروجی واقعی را قرار می‌دهم.

### ساخت Image

دستور ساخت باید مطابق روش مستندشده در مخزن و با مقادیر مناسب آرگومان‌های Build اجرا شود.

**خروجی واقعی دستور `docker build` را در این قسمت قرار می‌دهم.**

### بررسی تاریخچه Image

```bash
docker history <image>
```

این دستور تاریخچه مراحل ثبت‌شده در Image و اندازه هر لایه را نمایش می‌دهد.

**خروجی واقعی دستور `docker history` را در این قسمت قرار می‌دهم.**

## ۵. نتیجه‌گیری

با بررسی Dockerfile پروژه NetBox مشخص می‌شود که ساخت Image فقط شامل کپی کردن فایل‌ها نیست؛ بلکه آماده‌سازی وابستگی‌ها، تنظیم دسترسی‌ها، تولید فایل‌های استاتیک، تنظیم محیط اجرا و مشخص کردن فرایند راه‌اندازی را هم شامل می‌شود.

استفاده از Multi-stage Build نیز باعث می‌شود ابزارها و وابستگی‌های موردنیاز مرحله ساخت از فایل‌ها و کتابخانه‌های لازم برای Image نهایی جدا شوند.
