# هفته اول: نصب و راه‌اندازی پلاگین‌های NetBox با Docker

## ۱. هدف پروژه

هدف این پروژه نصب و فعال‌سازی دو پلاگین در NetBox و آشنایی با روش درست اضافه کردن پلاگین‌ها به یک پروژه Docker است.

در این پروژه از دو پلاگین استفاده کردم:

- **NetBox Topology Views:** برای نمایش گرافیکی تجهیزات شبکه و ارتباط بین آن‌ها.
- **NetBox Reorder Rack:** برای جابه‌جایی تجهیزات در رک و تغییر موقعیت آن‌ها.

در این تمرین علاوه بر نصب پلاگین‌ها، با ساخت Docker Image سفارشی، تنظیم Docker Compose و فعال کردن پلاگین‌ها در تنظیمات NetBox آشنا شدم.

## ۲. ساختار فایل‌های پروژه

فایل‌های این پروژه در پوشه `week1-plugins` قرار دارند.

```text
week1-plugins/
├── Dockerfile-Plugins
├── plugin_requirements.txt
├── docker-compose.override.yml
├── README.md
├── configuration/
│   └── plugins.py
└── screenshots/
```

توضیح فایل‌ها:

- `Dockerfile-Plugins`: دستورالعمل ساخت Docker Image سفارشی و نصب پلاگین‌ها.
- `plugin_requirements.txt`: نام و نسخه پلاگین‌هایی که باید نصب شوند.
- `docker-compose.override.yml`: تنظیم سرویس‌های NetBox برای استفاده از Image سفارشی.
- `configuration/plugins.py`: فعال کردن پلاگین‌ها در تنظیمات NetBox.
- `README.md`: گزارش مراحل انجام پروژه و پاسخ سؤال‌های فنی.
- `screenshots/`: محل نگهداری اسکرین‌شات‌های واقعی از نتیجه اجرای پلاگین‌ها.

## ۳. پلاگین‌های استفاده‌شده

در فایل `plugin_requirements.txt` این دو وابستگی تعریف شده‌اند:

```text
netbox-topology-views==4.7.0
netbox-reorder-rack==1.1.5
```

نسخه‌ها به‌صورت مشخص نوشته شده‌اند تا هنگام نصب مجدد، همان نسخه‌های تعیین‌شده نصب شوند و تغییر ناخواسته نسخه‌ها کمتر شود.

این نسخه‌ها در محیط پروژه استفاده و آزمایش شدند.

### پلاگین اول: NetBox Topology Views

این پلاگین امکان نمایش گرافیکی ارتباط بین تجهیزات شبکه را فراهم می‌کند. با استفاده از آن می‌توان ارتباطات تجهیزات را در قالب یک گراف مشاهده کرد.

در ابتدا صفحه توپولوژی خالی بود و چیزی نمایش داده نمی‌شد. پس از بررسی گزینه‌های صفحه و تنظیم فیلترها و تنظیمات نمایش، گراف تجهیزات نمایش داده شد.

### پلاگین دوم: NetBox Reorder Rack

این پلاگین امکان تغییر ترتیب و موقعیت تجهیزات در رک را فراهم می‌کند.

بعد از فعال‌سازی پلاگین، قابلیت جابه‌جایی تجهیزات را در صفحه رک آزمایش کردم. سپس صفحه جزئیات تجهیز را بررسی کردم تا تغییر موقعیت آن در NetBox مشخص باشد.

## ۴. ساخت Docker Image سفارشی

برای نصب پلاگین‌ها، فایل `Dockerfile-Plugins` را ایجاد کردم.

این فایل از Image پایه NetBox استفاده می‌کند:

```dockerfile
FROM docker.io/netboxcommunity/netbox:v4.7-5.1.1

COPY ./plugin_requirements.txt /opt/netbox/plugin_requirements.txt

RUN /usr/local/bin/uv pip install \
    -r /opt/netbox/plugin_requirements.txt

COPY configuration/plugins.py /etc/netbox/config/plugins.py

RUN mkdir -p /opt/netbox/netbox/static/netbox_topology_views/img

RUN DEBUG="true" \
    SECRET_KEY="dummydummydummydummydummydummydummydummy" \
    /opt/netbox/venv/bin/python \
    /opt/netbox/netbox/manage.py collectstatic --no-input
```

توضیح دستورات:

- `FROM`: مشخص می‌کند Image پایه برای ساخت Image جدید کدام است.
- `COPY`: فایل‌های موردنیاز را از محیط ساخت به مسیر مشخصی در Image منتقل می‌کند.
- `RUN`: دستورات لازم را هنگام ساخت Image اجرا می‌کند.
- `uv pip install`: وابستگی‌های مشخص‌شده در فایل requirements را نصب می‌کند.
- `collectstatic`: فایل‌های استاتیک موردنیاز NetBox و پلاگین‌ها را جمع‌آوری می‌کند.

همچنین مسیر مربوط به تصاویر استاتیک پلاگین Topology Views ایجاد شده است تا هنگام اجرای فرایند ساخت، مسیر موردنیاز وجود داشته باشد.

نکته مهم این است که `Dockerfile-Plugins` دستورالعمل ساخت Image است؛ خود این فایل به‌تنهایی یک کانتینر اجرا نمی‌کند.

## ۵. فعال کردن پلاگین‌ها

نصب بسته‌های پایتون به‌تنهایی برای فعال شدن پلاگین‌ها در NetBox کافی نیست. نام پلاگین‌ها باید در تنظیمات NetBox نیز ثبت شود.

محتوای فایل `configuration/plugins.py` به این شکل است:

```python
PLUGINS = [
    "netbox_topology_views",
    "netbox_reorder_rack",
]
```

در این قسمت، نام ماژول‌های پلاگین مشخص شده است تا NetBox آن‌ها را بارگذاری کند.

بنابراین دو مرحله اصلی داریم:

۱. نصب بسته‌های پلاگین در محیط پایتون داخل Docker Image.

۲. فعال کردن پلاگین‌ها در تنظیمات NetBox.

## ۶. تنظیم Docker Compose

برای استفاده از Image سفارشی، تنظیمات مربوط به سرویس‌های `netbox` و `netbox-worker` در فایل `docker-compose.override.yml` قرار گرفته‌اند.

بخش اصلی تنظیمات به این صورت است:

```yaml
services:
  netbox:
    image: netbox-custom:4.7.3
    build:
      context: .
      dockerfile: Dockerfile-Plugins
    ports:
      - "8000:8080"

  netbox-worker:
    image: netbox-custom:4.7.3
```

سرویس اصلی NetBox و سرویس Worker از یک Image سفارشی استفاده می‌کنند.

سرویس Worker وظایف پس‌زمینه را اجرا می‌کند و باید محیط نرم‌افزاری و تنظیمات موردنیاز پلاگین‌ها را داشته باشد.

در این تنظیمات، `netbox-custom:4.7.3` نام Image محلی انتخاب‌شده برای پروژه است. این نام با تگ Image پایه که در دستور `FROM` آمده است، یکسان نیست.

فایل اصلی `docker-compose.yml` پروژه NetBox Docker را تغییر ندادم و تنظیمات موردنیاز را در فایل Override قرار دادم.

**نکته اجرایی:** این Override برای استفاده همراه با فایل اصلی Compose در پوشه `netbox-docker` تنظیم شده است؛ بنابراین فایل Override به‌تنهایی یک پروژه مستقل Compose نیست.

## ۷. روش اجرای پروژه

مراحل اصلی کار به این صورت بود:

۱. تعریف نسخه پلاگین‌ها در `plugin_requirements.txt`.

۲. فعال کردن پلاگین‌ها در `configuration/plugins.py`.

۳. تعریف مراحل ساخت Image سفارشی در `Dockerfile-Plugins`.

۴. تنظیم سرویس‌های NetBox و Worker در فایل Override.

۵. ساخت Image و اجرای سرویس‌ها از طریق Docker Compose.

دستورهای مورد استفاده برای ساخت و اجرای پروژه:

```bash
cd ~/netbox-docker
docker compose build netbox
docker compose up -d
docker compose ps
```

برای مشاهده لاگ سرویس NetBox نیز می‌توان از دستور زیر استفاده کرد:

```bash
docker compose logs --tail=100 netbox
```

در پایان، وضعیت سرویس‌ها و فعال بودن پلاگین‌ها را در رابط وب NetBox بررسی کردم.

## ۸. مشکلات و راه‌حل‌ها

### مشکل اول: خالی بودن صفحه Topology Views

در ابتدا صفحه توپولوژی خالی بود و گراف تجهیزات نمایش داده نمی‌شد.

با بررسی تنظیمات صفحه، فیلترها و گزینه‌های نمایش، مشکل برطرف شد و گراف تجهیزات قابل مشاهده شد.

### مشکل دوم: مشخص نبودن نتیجه جابه‌جایی تجهیزات رک

بعد از استفاده از قابلیت جابه‌جایی تجهیزات، صفحه جزئیات دستگاه را نیز بررسی کردم تا مقدار رک و موقعیت دستگاه مشخص باشد.

این بررسی کمک کرد مطمئن شوم تغییر موقعیت فقط در ظاهر صفحه باقی نمانده و مقدار موقعیت در اطلاعات دستگاه نیز منعکس شده است.

### نکته مربوط به Docker Image و Container

در این پروژه نصب پلاگین‌ها در فرایند ساخت Image تعریف شد، نه فقط با اجرای یک دستور نصب دستی در کانتینر در حال اجرا.

به همین دلیل می‌توان با ساخت مجدد کانتینر از Image سفارشی، محیط دارای پلاگین‌ها را دوباره ایجاد کرد.

## ۹. پاسخ به سؤال‌های فنی

### سؤال اول: چرا نصب پلاگین فقط داخل کانتینر روش مناسبی نیست؟

اگر پلاگین را به‌صورت دستی داخل یک کانتینر در حال اجرا نصب کنیم، تغییر ایجادشده معمولاً فقط در همان کانتینر باقی می‌ماند. اگر آن کانتینر حذف شود و یک کانتینر جدید از Image قبلی ساخته شود، نصب دستی پلاگین از بین می‌رود.

در این روش، مراحل نصب نیز داخل Dockerfile ثبت نشده‌اند؛ بنابراین بازسازی همان محیط دشوارتر می‌شود.

روش بهتر این است که نصب پلاگین در Dockerfile تعریف شود و یک Docker Image سفارشی ساخته شود. در این صورت، نصب پلاگین بخشی از فرایند ساخت Image خواهد بود و می‌توان از همان Image برای ایجاد کانتینرهای جدید استفاده کرد.

### سؤال دوم: چرا بهتر است نسخه پلاگین‌ها را مشخص کنیم؟

اگر نسخه پلاگین‌ها مشخص نباشد، ممکن است در نصب‌های مختلف نسخه‌های متفاوتی دریافت شود. تغییر نسخه می‌تواند باعث تفاوت در رفتار برنامه یا ناسازگاری با نسخه NetBox شود.

با مشخص کردن نسخه‌ها در `plugin_requirements.txt`، نصب قابل پیش‌بینی‌تر می‌شود و بازسازی محیط آسان‌تر خواهد بود.

البته برای اطمینان از سازگاری کامل، نسخه پلاگین‌ها باید با نسخه NetBox و وابستگی‌های آن نیز بررسی و آزمایش شود.

### سؤال سوم: چرا باید پلاگین در سرویس‌های netbox و netbox-worker در دسترس باشد؟

سرویس `netbox` رابط اصلی برنامه را اجرا می‌کند و درخواست‌های کاربران از طریق آن پردازش می‌شوند.

سرویس `netbox-worker` وظایف پس‌زمینه را اجرا می‌کند. این سرویس نیز به محیط نرم‌افزاری و تنظیمات موردنیاز برنامه وابسته است.

اگر پلاگین فقط در یکی از این سرویس‌ها نصب یا فعال باشد، ممکن است بین محیط اجرای برنامه و محیط اجرای وظایف پس‌زمینه اختلاف ایجاد شود.

به همین دلیل هر دو سرویس را روی Image سفارشی دارای پلاگین‌ها تنظیم کردم. سرویس‌های دیتابیس و Redis یا Valkey برای نصب این بسته‌های پایتون نیازی به استفاده از همین Image سفارشی ندارند.

### سؤال چهارم: چه تفاوتی بین نصب پلاگین و فعال کردن آن وجود دارد؟

نصب پلاگین یعنی بسته و کدهای موردنیاز آن در محیط پایتون در دسترس قرار بگیرند.

فعال کردن پلاگین یعنی نام آن در تنظیمات NetBox، مانند `PLUGINS`، ثبت شود تا برنامه آن را بارگذاری کند.

بنابراین ممکن است بسته‌ای نصب شده باشد، اما تا زمانی که تنظیمات لازم انجام نشود، قابلیت‌های آن در NetBox فعال نشوند.

در این پروژه، نصب در Dockerfile و فعال‌سازی در `configuration/plugins.py` انجام شد.

### سؤال پنجم: تفاوت قابلیت پیش‌فرض Rack با پلاگین Reorder Rack چیست؟

نمای رک در NetBox برای مشاهده تجهیزات نصب‌شده در رک، ارتفاع تجهیزات و موقعیت آن‌ها کاربرد دارد.

پلاگین Reorder Rack قابلیت جابه‌جایی و مرتب‌سازی تجهیزات در رک را ساده‌تر می‌کند.

هنگامی که موقعیت یک دستگاه تغییر می‌کند، اطلاعات موقعیت آن در NetBox به‌روزرسانی می‌شود. این تغییر به معنی جابه‌جایی فیزیکی دستگاه نیست؛ بلکه اطلاعات ثبت‌شده درباره محل نصب آن را تغییر می‌دهد.

## ۱۰. نتیجه‌گیری

در این پروژه با روش نصب و فعال‌سازی پلاگین‌ها در NetBox مبتنی بر Docker آشنا شدم.

مهم‌ترین نکته این بود که برای داشتن یک محیط قابل بازسازی، بهتر است وابستگی‌ها و مراحل نصب در Dockerfile تعریف شوند و تنظیمات فعال‌سازی پلاگین‌ها نیز به‌صورت مشخص نگهداری شوند.

همچنین تفاوت بین Docker Image و Container، نقش Docker Compose و دلیل استفاده از Image مشترک برای سرویس‌های NetBox و Worker را بهتر درک کردم.
